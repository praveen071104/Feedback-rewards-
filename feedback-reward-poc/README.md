# Customer Feedback Reward Recommendation System

A local showcase POC: React + TypeScript + Vite, FastAPI, and two independently trained scikit-learn classifiers. No external AI service or API key is required. This is not a production reward system and does not issue rewards.

## Flow and business rules

```text
Customer feedback -> Sentiment model -> Positive / Neutral / Negative
                  -> Genuine-feedback model + decision rules -> Yes / No
                  -> Reward recommendation -> Eligible / Not eligible
```

Each model is a separate `Pipeline(TfidfVectorizer, LogisticRegression)`, with unigram/bigram TF-IDF features, balanced class weights, and a fixed random seed. Each saved joblib file includes its own vectorizer and classifier. The genuine classifier sees the feedback text, not the sentiment prediction.

Eligibility is exactly `genuine_feedback == "Yes"` after decision rules. Positive sentiment never grants a reward by itself; specific positive, neutral, and negative feedback can qualify. Generic words and greetings are not disqualifiers when accompanied by useful information. Rules are evaluated in this order:

1. **Contextual stock feedback:** a recognised product term plus an availability observation or restocking request must also provide useful context, such as timing, recurrence, impact, or a contextual improvement request. The context must occur in the same sentence or in an immediately following restocking request. "cakes sold out", "nice cakes but no stock", and "pls restock bread" are **Not eligible**, even if the model guesses Yes. "cakes sold out by 5pm", "cakes always soldout pls restock", and "cakes sold out. please restock before lunch" are **Eligible**. Your original longer cakes and bakery examples also qualify. This is about additional information, not perfect grammar or sentence length; padding and repetition do not qualify. Simple negation suppresses the stock rule rather than interpreting "not sold out" as a shortage. Context is detected using explicit phrase patterns, not general semantic reasoning.
2. **Fallback minimum-detail check:** other feedback needs either two distinct recognised content words, or at least four distinct content words with one recognised by the model. Only alphabetic tokens count; English stopwords, greetings, generic opinions, and generic retail terms are excluded from the count, not used as a veto. This lets unfamiliar details contribute without requiring every word in the tiny training vocabulary. Failure sets the final genuine label to No.
3. **Model fallback:** if the detail check passes and no stock rule applies, the genuine classifier decides.

Greetings alone, generic praise, repeated keywords, detailed appreciation, and equivalent short/formal stock comments are regression-tested. The dataset's `reward_eligible` column is audited against the rule, not used as a model input or separate training target. No models were retrained for these rule changes.

This check addresses a real model failure: text with no TF-IDF features such as "Hi" previously defaulted to Yes from the classifier's intercept. Stopwords alone or a repeated known keyword could also cause false approvals. The safeguard uses distinct supported content words, not just message length. It is a heuristic, not semantic understanding: useful unfamiliar wording can be rejected and combinations of recognised keywords can still fool it. Better labelled data and independent evaluation remain necessary.

The reason is a transparent rule-based explanation of the prediction, not an LLM explanation or independently verified assessment of actionability. `genuine_feedback` is a synthetic proxy for usefulness, not proof that a person or statement is authentic.

## Setup on Windows PowerShell

Prerequisites: Python 3.11+ (tested with 3.13), Node.js 22.12+ or a supported newer LTS, and npm. Run these commands from this project folder. The CSV has already been copied into `backend/data`; the original is unchanged.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend/requirements.txt
.\.venv\Scripts\python.exe backend/train_sentiment.py
.\.venv\Scripts\python.exe backend/train_genuine.py
npm --prefix frontend ci
```

No virtual-environment activation is required. Both model files are created beside the scripts regardless of the working directory. To train on another CSV, pass `--data "C:\path\dataset.csv"` to each script. Restart FastAPI after retraining. Only load trusted, locally generated joblib files; pickle-based files can execute code.

Terminal 1, from this project folder:

```powershell
.\.venv\Scripts\python.exe -m uvicorn main:app --app-dir backend --host 127.0.0.1 --port 8000 --reload
```

Terminal 2, from this project folder:

```powershell
npm --prefix frontend run dev
```

- App: http://127.0.0.1:5173 (use the URL Vite prints if that port is occupied).
- API documentation: http://127.0.0.1:8000/docs
- Readiness: http://127.0.0.1:8000/health

The frontend sends requests to `/api/predict`; Vite proxies to FastAPI's `/predict`, avoiding cross-origin browser requests. If port 8000 is occupied, choose another API port and update both proxy targets in `frontend/vite.config.ts`. Stop either server with Ctrl+C. Keep both services bound to localhost.

On macOS/Linux, replace `.\.venv\Scripts\python.exe` with `.venv/bin/python` and use `python3` to create the environment. Other commands are the same.

## API

`POST /predict`, content type `application/json`:

```json
{ "feedback": "The store lighting is too dim and causes eye strain while shopping." }
```

Response shape (illustrative probabilities, not a promised output):

```json
{
  "sentiment": "Negative",
  "sentimentConfidence": 0.91,
  "genuineFeedback": "Yes",
  "genuineConfidence": 0.95,
  "rewardEligible": true,
  "reason": "Predicted to be genuine, specific and useful feedback; eligible regardless of sentiment."
}
```

Confidence is the displayed class's `predict_proba` value in [0, 1]. When a rule sets No or Yes, genuine confidence remains the original model's probability for that displayed label, which may be below 50%; it is not fabricated certainty in the rule. The reason explicitly identifies the rule. The UI rounds probabilities to percentages. These values are not calibrated accuracy. Actual output depends on the trained data, including labels for mixed feedback.

```powershell
Invoke-RestMethod -Uri http://127.0.0.1:8000/predict -Method Post -ContentType 'application/json' -Body '{"feedback":"The checkout queue is very long between 5 PM and 6 PM."}'
```

Input must be a string of 1-5,000 characters containing at least one letter. Blank, numeric-only, malformed, oversized, and extra-field requests return 422. Unavailable models return 503 with training instructions. `/health` reports `modelsLoaded`; its HTTP 200 indicates that the API is reachable, not necessarily model readiness. Requests are not saved to a database or deliberately logged as feedback content.

## Validation

```powershell
.\.venv\Scripts\python.exe -m pytest backend/tests -q
npm --prefix frontend run build
npm --prefix frontend run lint
```

Train both models before running tests. Tests cover generic feedback, useful positive/negative/mixed feedback, exact response fields, probabilities, the sentiment-independent reward rule, invalid requests, readiness, and unavailable models.

With both servers running, run the repeatable browser checks:

```powershell
npm --prefix frontend run test:e2e
```

On Windows the tests use installed Microsoft Edge. On other platforms they use Playwright Chromium; install it from `frontend` with `npx playwright install chromium`. To use Chromium on Windows, install it the same way and set `$env:PLAYWRIGHT_CHANNEL = 'chromium'` before running the tests. The tests expect the frontend on port 5173; update `baseURL` in `frontend/playwright.config.ts` if necessary.

The browser tests exercise the real API, verify reward examples, greeting/nonsense rejection, detailed appreciation with and without greetings, generic stock rejection versus contextual stock acceptance, invalid-input disabling, loading locks, simulated 503 recovery, and layouts at 320, 390, 768, and 1440 pixels. They regenerate the screenshots below. The suite contains **67 backend tests and 2 browser tests**. The backend test runner emits two dependency deprecation warnings.

For a local production-build preview, keep FastAPI running:

```powershell
npm --prefix frontend run build
npm --prefix frontend run preview
```

This preview also proxies `/api`. A deployed static build would need its own reverse proxy; deployment, authentication, rate limiting, and reward fulfilment are outside this POC.

## Dataset quality and limitations

The supplied 300-row CSV has only **25 unique feedback texts**. **10 text groups have conflicting sentiment labels**; for example, short generic comments occur under different sentiments. No labels were silently corrected. Genuine/reward labels agree for all rows.

Training evaluates with a deterministic 25% grouped holdout (89 rows), keeping identical normalized feedback text out of both sides of the split. TF-IDF is fitted only on the training partition for evaluation. Then a fresh final pipeline is trained on all rows and saved for the demo.

| Model | Grouped holdout accuracy |
| --- | ---: |
| Sentiment | 21.3% |
| Genuine feedback | 62.9% |

These low scores are reported deliberately. The held-out genuine classifier predicts every held-out example as Yes, with zero recall for No. The dataset cannot establish reliable generalization; familiar examples may look convincing while unseen wording, generic phrases, nonsense, or out-of-vocabulary text can be misclassified. The final models have seen the demo samples, so passing those regression tests is **not** evidence of unseen-data accuracy. Full per-class metrics and conflict counts are in the generated JSON reports. Small changes to data or dependencies may change results.

The metrics above evaluate the original classifiers, not the combined model and decision rules. The rules do not claim improved holdout accuracy. The stock rule uses an explicit product lexicon and phrase patterns, not general semantic understanding; unfamiliar products, typos, complex negation, and other types of short useful feedback can still be missed. Keyword combinations can still fool the system. Wider representative training data and independent evaluation are needed to solve wording sensitivity more generally.

Do not use this to make real reward decisions. Improve unique examples and label consistency, collect representative held-out data, assess per-class performance and calibration, and include human review before considering a real pilot. No inference-time duplicate detection is implemented; grouped evaluation only prevents duplicate leakage in measurement.
